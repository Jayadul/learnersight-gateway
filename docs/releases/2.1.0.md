# Release 2.1.0 — Tag grammar, gateway auth, startup readiness (2026-09-02)

A small, deliberately **breaking** release. Every third-party integrator must change
both their message templates and their credentials before this is deployed.

## Overview

Three changes, bundled on purpose so integrators migrate once instead of twice:

1. The `/sendtext` tag grammar is replaced — every tag now names the specific gateway it
   uses.
2. Gateway credentials move off the SMS channel config into their own record.
3. The login failure seen after `docker compose pull` is root-caused and fixed.

## Breaking changes

### Tag grammar

Every tag is `[type:label::content]`. The whole previous grammar is gone — **not
deprecated, removed**:

| Removed | Replacement |
|---|---|
| `[sms::text]` | `[sms:revemain::text]` |
| `[wp::text]` | `[wp:waprimary::text]` |
| `[wp::text\|\|url]` | `[wp:waprimary::text\|\|url]` |
| `[sms-wp::text]`, `[smswp::text]` | `[sms:revemain-wp:waprimary::text]` |
| `[wpmedia::…]` | `[wp:waprimary::text\|\|url]` |
| `[sms_label:a::text]` and every `_label:` form | `[sms:a::text]` |

The label is mandatory inside a tag. **Sending no tag at all** is the only remaining way
to reach a default channel, and still means "plain SMS with the whole body on the default
SMS channel". Rejection reasons name the removed form and its replacement — anyone hitting
one is mid-migration, not guessing.

Unknown labels, and labels naming an inactive channel, are now rejected at accept time
with `101 REJECTD` and a `Reason`. Previously they were skipped during dispatch, so the
caller got `ACCEPTD` for a message that was never sent and the only trace was a warning in
Seq.

### Gateway credentials

`apikey`/`secretkey` are validated against the new single-row `gateway_credentials`
table, not the default SMS `ChannelConfig`. **Credentials that worked before 2.1 stop
working.** Rationale and consequences: [adr/0007](../adr/0007-decouple-gateway-auth-from-channel-config.md).

New admin screen at **Configuration → Gateway Credentials** (SuperAdmin): username and
both keys shown, each key behind a reveal toggle with copy and regenerate buttons. They
are readable on purpose — the pair has to be handed to an integrator and the column is
ciphertext, so a masked screen could not do its job. A side panel gives the endpoint and
a ready-to-copy cURL built from the live values. Every field of the update is optional and
only changed fields are sent, so changing the username alone cannot blank the keys — the
Release 2 channel-update bug, not repeated.

Seeded from `Seed:GatewayCredentials` (`Username`, `ApiKey`, `SecretKey`) on a fresh
database, then never touched again. Without the section the row is not created and
`/sendtext` rejects everything; the seeder logs that at Error rather than failing the boot.

## Fixed

**Login fails after `docker compose pull`.** Not seed-data loss, which is where the
investigation was pointed. `web` declared `depends_on: [api]`, the short form, which waits
only for the API *container to start* — not for it to be ready. Migrations and seeding run
to completion before `app.Run()`, so on a fresh pull the API is unreachable for as long as
they take, while nginx is already serving the login page and answering `/api/*` with
**502**. The sign-in screen mapped every non-401 to "Sign in failed. Please try again.",
which reads exactly like a rejected password.

Three parts to the fix:

- New anonymous `GET /health`, and a `HEALTHCHECK` in the API Dockerfile (90s start
  period, which covers a first run against an empty database).
- `web` now waits on `api: condition: service_healthy` in both `docker-compose.yml` and
  `deploy/docker-compose.yml`.
- Sign-in distinguishes a connection failure or 5xx from a 401: "The gateway is still
  starting up. Give it a moment and try again."

The startup gate the original report suspected was missing already existed — it is what
creates the window, not what was absent.

## Also changed

- Gateway Simulator lists the installation's **actual** gateway labels, loaded live, with
  a ready-to-copy tag per channel. With labels mandatory, a guide showing only placeholder
  slugs would document tags that reject. Inactive channels are hidden — naming one fails.
- Gateway Simulator pre-fills apikey/secretkey from the gateway credentials, so testing is
  one click. It previously told you to copy them from Channels by hand, which is no longer
  even the right screen.
- The guide documents one voice form, `[call:LABEL::CAMPAIGN_ID||LOT]`. The parser still
  accepts a bare campaign id and falls back to the channel's configured lot, but showing
  both invited integrators to omit the lot without meaning to.
- The simulator's prefilled example deliberately contains **no** `call` tag: pressing Send
  on a one-click example must not place a real billed outbound call.
- Channel cards show the new tag form; voice cards say `your-campaign-id` rather than
  `your message`, which was never what a voice tag carries.
- Docs updated for the removed grammar, the new auth source and the new table: `api.md`,
  `architecture.md`, `database.md`, `testing.md`, `postman/`.

## Tests

50 backend tests (`dotnet test`), up from 34. New: every 2.1 tag form, the no-tag path, a
rejection test per removed 2.0 form, and `GatewayCredentialService`'s partial-update
contract plus its unreadable-ciphertext path.

## Deployment notes

1. **Hand integrators the new credentials and templates before deploying.** Both break at
   the same moment.
2. `Seed:GatewayCredentials` must be added to `appsettings*.json` before first start on a
   fresh database, or `/sendtext` rejects everything.
3. Rebuild and push both images — the API image carries the healthcheck and the web image
   the new simulator page. Retag `netzero-gateway-*` → `learnersight/*` first
   (`deployment.md`).
4. Existing databases: the migration only adds `gateway_credentials`. On an existing
   database the seeder **will** create the row, since the table starts empty.

## Lessons

- **The reported symptom named the layer.** "Sign in failed. Please try again." only
  appears for a non-401, which ruled out missing seed data in one grep and pointed
  straight at the proxy. The prompt's hypothesis — a seeding race — was the opposite of
  the truth: the gate was already there, and the gate is what opens the window. Reading
  the exact error string first was worth more than any amount of reasoning about the
  seeder.
- **A gate that blocks startup needs a readiness signal**, or everything in front of it
  fails in a way that looks like something else. `depends_on` without a condition promises
  less than it appears to.
- **Silent skip vs. loud reject, again.** An unresolvable label was a dispatch-time
  warning; the caller saw success. The same reasoning that made unknown *tags* reject in
  2.0 applies to unknown *labels*, and it took making labels mandatory to notice the gap.
