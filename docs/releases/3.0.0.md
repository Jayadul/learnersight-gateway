# Release 3.0.0 — Multi-provider channels, balances, delivery status (2026-09-06)

Backend `feature/r3-*` · Frontend `feature/r3-*` · Migrations `AddProviderAndDispatchJobRecipients`,
`AddChannelBalanceCache`, `AddRecipientResendLink`

## Overview

Until this release a channel type implied its vendor: SMS meant REVE, WhatsApp meant
WaTrend, Voice meant NetZero. Release 3 breaks that assumption and builds three things on
top of it — more providers, their remaining credit, and what actually became of each
message.

Shipped in three phases, each tested before the next began:

| Phase | Scope |
|---|---|
| R3.0 | Provider abstraction, `dispatch_job_recipients`, per-channel base URLs |
| R3.1 | GenNet, Chithi and both NetZero Inbox WhatsApp APIs; provider balances |
| R3.2 | Delivery status sync, nightly job, per-recipient UI, recipient resend |

**Not breaking for integrators.** The `/sendtext` contract is unchanged. A tag names a
channel label, and which vendor that label uses is an admin concern.

## Added

### Multi-provider channels (ADR 0008)

`ChannelConfig.Provider` names the vendor, and `IChannelSenderFactory` resolves on
`(ChannelType, Provider, HandlesMedia)`. A channel naming a provider with no registered
sender **throws** rather than substituting another vendor — substituting would send
through the wrong account and bill it. Duplicate registrations fail at startup instead of
resolving by DI order, and a provider that cannot serve a channel type is rejected when
the channel is saved rather than when a real message is waiting.

Selectable providers: **SMS** — REVE, GenNet, Chithi · **WhatsApp** — WaTrend, NetZero
Inbox (v1), NetZero Inbox (QR) · **Voice** — NetZero Voice.

### Recipient formats are per provider

Numbers are stored canonically (digits, country code, no plus). The new providers
disagree, in different directions:

| Provider | On the wire |
|---|---|
| REVE, WaTrend, NetZero Voice, Chithi, NetZero Inbox QR | `8801700000001` |
| GenNet | `01700000001` |
| NetZero Inbox v1 | `+8801700000001` |

Chithi shares GenNet's `api_token`, `sid` and API family but neither its number format
nor its request shape — GenNet takes an array at `/send-sms/bulk`, Chithi one `msisdn`
per call. Shared credentials say nothing about the wire format.

### Two NetZero Inbox WhatsApp APIs

They share a host and a token and nothing else: v1 is a JSON `POST` over https with no
sender number, the QR device API is a `GET` query string over plain http carrying the
linked device's `from`. Separate providers, not a mode flag — the recipient format is
resolved from the provider alone. Neither supports media; both refuse a media send rather
than guess a request shape the vendor has not documented.

### Provider balances

REVE, GenNet and Chithi report one behind a single provider-agnostic result. A null credit
limit means the provider has no such concept, **not zero** — only REVE reports one. Cached
on `channel_configs`, refreshed every 15 minutes to match the dashboard's existing cycle;
reads never call a provider, since one slow vendor would stall a page showing six
channels. A failed refresh keeps the last known figure and marks it stale rather than
blanking, which would read as an empty account.

REVE's balance is on a different host and port from its send endpoint, so it is
configured separately (`balanceBaseUrl`). Its session cookie has no refresh endpoint by
design: when it expires the check fails clearly and an admin pastes a fresh one.

### `dispatch_job_recipients`

One row per recipient per job. SMS and Voice batch every number into a single job, so
until now a partly delivered batch had nowhere to record which numbers arrived. Job
status is what the provider said at hand-off; recipient status is what happened
afterwards, and the two can legitimately disagree.

### Delivery status sync

REVE, Chithi and NetZero Voice answer what became of a message. **GenNet has no status
endpoint**, so its rows stay `Pending`. Runs nightly at 00:00 Dhaka for the previous full
day, and on demand per channel over a chosen window.

A reported delivery failure is written to the row. A **rejected request** — expired
session, bad credentials — says nothing about any recipient and leaves every row
untouched including `last_checked_at`, so the next run retries the same window. An
unrecognised state is `Unknown`, never guessed into `Failed`.

Voice has no correlation id at all: records match by number plus a ±5 minute tolerance
around dispatch, and a row matching two records is left unresolved and logged rather than
guessed.

### Resend

Recipient-level, because retrying a batched job would send again to everyone it already
reached. Every attempt creates a new job and rows linked by `resent_from_recipient_id` —
a retry that succeeds must not erase the evidence the first attempt failed. Same channel
type only; ManualSend tier, not SuperAdmin.

## Fixed

- **`authorization.json` silently outranked every environment variable.** It was added to
  configuration *after* `CreateBuilder` registered the environment source, and the last
  source wins. That is why `Providers__Voice__BaseUrl` could be set in the container,
  confirmed with `printenv`, and still be ignored at dispatch. Any deployment carrying
  such an override should be checked — it has never taken effect.
- **The `baseUrl` field the admin UI collects was dead.** Read by nothing since it
  shipped; it now sets the channel's endpoint, falling back to the configured default.
- **`VoiceSender` overwrote `CampaignId` with the provider's task id**, so the delivery
  log showed a GUID where the requested campaign belonged.
- **Credentials were masked by an exact list of five field names.** Every provider added
  afterwards served its credential in the clear through the admin API — which is exactly
  what happened when the R3.1 channels were seeded. Masking now matches the shape of the
  field name.
- **Manual send accepted an empty recipient list**, returning 202 and then resolving to
  Failed. Now refused before anything is queued.
- **`deploy/docker-compose.yml` had no `mediadata` volume**, so Media Library files
  vanished on a client's next `docker compose pull`. It was also missing
  `Media__PublicBaseUrl`, which meant media links pointed at the dev API.

## Tests

135 backend tests, up from 50 at 2.1.0. New coverage: sender resolution, per-provider
recipient formats, the three new senders, balance caching, the status sync providers
(including that a rejected request touches nothing and that voice refuses an ambiguous
match), resend's audit trail and type restriction, and credential masking by field shape.

## Deployment notes

- Three migrations, applied at startup. The provider backfill is **required**: the column
  stores the enum as text and the generated default is `''`, which parses back to
  nothing, so without it every pre-R3 channel becomes unreadable on the first query.
- GenNet, Chithi and both Inbox channels are seeded **inactive**. Activate each once its
  credentials are confirmed; an active channel with placeholder credentials fails real
  messages.
- The new channels must carry a `baseUrl` — unlike REVE/WaTrend/Voice they have no
  central default to fall back on.
- Provider secrets are still seeded in `appsettings.json` in plaintext (R1 debt item 4),
  now across seven channels. Rotate the REVE session cookie, the shared GenNet/Chithi
  `api_token` and the NetZero Inbox token before they carry production traffic.

## Lessons

- **Shared credentials say nothing about a shared contract.** GenNet and Chithi issue one
  `api_token` and one `sid` between them and sit on the same API family; they still
  disagree on number format and request shape. Treating them as one implementation would
  have sent to wrong numbers.
- **Reading the config file found a leak that code review would not.** Being granted
  access to `appsettings.json` to add the seed block is what surfaced the credentials
  being served unmasked — the failure was in a fixed allowlist that nothing pointed at.
- **The country code is 880, not 88.** Caught by a test, not by reading; an off-by-one
  country code silently produced a different phone number.
- **Phase boundaries held.** Each phase ended green and deployed before the next started,
  so when the QR API had to be added back after R3.1, it landed on a foundation that took
  it additively.
